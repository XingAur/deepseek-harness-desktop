# Windows 完整安装生命周期 E2E 设计

## 背景

DeepSeek Harness Desktop 已有 Windows 安装后 E2E 基础设施，并覆盖干净安装、首次启动准备 Runtime、温启动、创建两个会话、无刷新切换和重启恢复。但现有用例尚未进入 GitHub Actions，也没有真实验证覆盖升级、Profile/Runtime 状态保留、卸载器的两个数据删除选项以及失败后的脱敏证据。

P0.2 的目标不是再创建一套并行测试框架，而是扩展现有 `e2e/`、`scripts/e2e/` 和 NSIS 隔离安装能力，把普通用户最关键的安装、首次成功对话、升级和卸载闭环变成可重复的发布门禁。

## 目标

- PR 上以确定性本地 Runtime 和模型夹具验证安装后核心路径。
- 每日或 Release Candidate 验证基线版本到候选版本的真实 NSIS 覆盖升级。
- 证明升级不会丢失 Profile、last-known-good、Runtime、项目、会话和模型路由。
- 自动验证卸载器的保留数据、只删除应用数据、删除应用数据和项目三个有效状态。
- 所有删除操作限制在明确标记的 E2E 根目录，不允许测试扩大到开发机真实数据。
- 失败时生成可定位阶段且不包含凭证、绝对用户路径或对话正文的报告。

## 非目标

- 不在普通 PR 中调用真实 DeepSeek API。
- 不依赖 GitHub Release、外网下载或上一版本公开资产完成确定性升级测试。
- 不把完整生命周期塞入现有双平台构建 Job。
- 不用同版本重装代替版本升级验证。
- 不自动完成安装版连续 30 轮人工 Release Candidate 验收。
- 不修改产品的默认卸载语义或项目删除安全模型。

## 1. 执行分层

安装生命周期使用独立 Windows 工作流，按运行成本分为两层。

### PR 快速门禁

只在安装器、Runtime、Session、Profile、项目、E2E 支撑代码或相关工作流变化时运行：

```text
构建候选安装包
→ 静默安装
→ 首次启动并准备 Runtime
→ 创建 Unicode 项目
→ 创建两个会话并验证无需刷新
→ 完全退出并重新启动
→ 验证项目和会话恢复
→ 默认卸载并验证用户数据保留
```

PR 门禁使用单个候选安装包，不执行多轮安装和完整卸载矩阵。这样保留最重要的回归保护，同时避免每个 PR 都被 Windows Runner 上耗时且波动较大的完整生命周期阻塞。

### 每日与手动 RC 门禁

定时任务和 `workflow_dispatch` 执行完整路径：

```text
构建基线版和候选版
→ 安装基线版并创建可恢复状态
→ 覆盖安装候选版
→ 比较升级前后状态
→ 升级后继续对话并再次重启
→ 逐一执行卸载矩阵
→ 生成脱敏机器报告
```

手动 RC 可以额外接收上一正式 Release 安装包，增加一次真实历史版本兼容验证。该验证不取代确定性双包测试，也不作为普通 PR 前置条件。

真实 DeepSeek API 测试仍只能通过显式手动任务运行，凭证来自 GitHub Secret，并使用独立的日志脱敏策略。

## 2. 确定性双安装包

完整升级测试从同一提交构建两个安装包：

- **基线版**：使用低于当前桌面版本的临时版本号；
- **候选版**：使用仓库当前正式桌面版本号。

两个安装包共用相同应用源码、确定性 Runtime、模型夹具和 E2E 配置，只有安装包版本身份不同。这样能够真实触发 NSIS 更新模式，同时避免业务代码差异干扰升级结果。

构建脚本生成临时 Tauri 配置覆盖版本，不修改或提交 `package.json`、`Cargo.toml` 和 `release/versions.json`。临时版本必须由当前 SemVer 安全派生并明确小于候选版本；若当前版本无法按常规 patch 递减，构建脚本必须使用经过 Windows 安装器版本规则验证的备用基线版本，不能依赖字符串排序。

每个制品都写入构建元数据，至少包含：

- 场景身份：`baseline` 或 `candidate`；
- 桌面版本；
- Runtime 版本和清单哈希；
- 安装包绝对路径的脱敏表示；
- 安装包 SHA-256；
- 源提交；
- 构建时间。

安装包、元数据和测试使用同一个 E2E 产品名、Bundle ID 和受控安装根。生产产品注册表和真实用户数据根不得进入测试范围。

## 3. 升级前状态快照

基线版首次启动并完成两个会话后，测试保存一份结构化快照。快照只记录验证所需的稳定标识和哈希：

### 安装身份

- 注册表产品版本；
- 安装根占位符；
- 应用二进制版本和 SHA-256。

### Runtime 和 Generation

- `state/provisioning.json` 中的 Runtime 版本和 `activeDir`；
- 已验证清单哈希；
- 最新成功 Generation 的 ID、阶段和耗时；
- Runtime 进程身份和本机端口只用于运行期验证，不写入最终公开报告。

### Profile

- 当前 Profile ID；
- last-known-good Profile ID；
- Profile 配置修订；
- `pending` 必须为空。

### 项目和会话

- Unicode 项目的 Workspace ID；
- 项目目录的占位符表示；
- 专用校验文件的 SHA-256；
- 两个官方 Session ID；
- 会话标题的测试标记；
- 每个会话的最后事件序号或等价稳定游标。

### 模型配置

- Provider 和 Route 的稳定 ID；
- 推荐模型配置是否存在；
- 不读取和不记录 API Key、认证头、提示词或回复正文。

## 4. 覆盖升级验收

保存基线快照后，测试完全退出桌面端和 Runtime，再以被动模式安装候选包。升级完成后启动候选版，并验证：

1. 注册表产品版本和应用二进制身份已切换到候选版。
2. 安装根与固定数据根保持不变。
3. 安装阶段没有下载或解压 Runtime，也没有调用应用数据或项目清理模式。
4. Runtime 版本、活动目录和已验证制品身份继续有效；不产生无理由的重复准备。
5. 当前 Profile、last-known-good Profile 和配置修订保持一致，且没有遗留 `pending`。
6. Unicode 项目的 Workspace ID、目录和校验文件保持不变。
7. 两个会话继续使用原 Session ID，标题和历史可直接显示。
8. 升级后发送第三条消息，标题和回复无需刷新即可出现。
9. 再次完全退出并启动后，项目、Profile、模型路由和三个会话状态仍可恢复。

Generation ID 允许因重启发生变化，但新的 Generation 必须进入 `active`，且不得破坏之前的 last-known-good 证据。若当前测试 Runtime 与候选应用确实要求升级，应改用专门的 Runtime 升级场景；本用例不能把无关 Runtime 版本变化混入桌面覆盖升级。

升级失败阶段使用稳定枚举：

```text
baseline-build
candidate-build
baseline-install
baseline-first-launch
snapshot-before-upgrade
candidate-install
candidate-first-launch
state-comparison
post-upgrade-session
second-restart
```

## 5. 卸载矩阵

卸载器已有两个默认不勾选的选项：删除应用数据、同时删除已登记的本地项目。项目删除依赖应用数据删除，因此存在三个有效结果和一个必须验证的联动规则。

| 删除应用数据 | 删除本地项目 | 预期结果 |
| --- | --- | --- |
| 否 | 否 | 程序、快捷方式和卸载注册表删除；Profile、Runtime、会话和项目全部保留 |
| 是 | 否 | 应用数据删除；项目源码保留且内容不变 |
| 是 | 是 | 应用数据和已登记项目全部删除 |
| 否 | 是 | 不允许形成；选择项目删除时必须自动选择应用数据删除 |

测试命令对应为：

- `/P`：默认保留；
- `/P /DELETEAPPDATA`：只删除应用数据；
- `/P /DELETEPROJECTS`：删除项目，并由卸载器隐含应用数据删除。

每个有效结果使用独立安装和独立数据，不能复用上一卸载场景的残留状态。除校验程序文件、快捷方式和卸载注册表已移除外，还必须验证桌面进程、Runtime 进程和记录端口均已关闭。

应用数据采用原子移出和后台释放空间时，测试允许清理异步完成，但必须有明确超时并验证最终目录状态。默认保留分支和只删除应用数据分支必须使用哨兵文件哈希证明未选择的内容没有变化。

## 6. 删除安全边界

所有场景使用 E2E 专属绝对根目录，并在可能被删除的根写入仅由测试环境创建的 E2E 所有权标记。项目删除场景只创建在类似以下受控位置：

```text
$E2E_ROOT/projects-owned/含中文 Ω/
```

自动化执行任何删除前必须验证：

1. 安装记录来自当前场景；
2. 安装根、数据根和项目根均为绝对路径；
3. 目标位于预期 E2E 父目录内；
4. 数据根存在 `.dsh-e2e-owned` 标记；
5. 项目存在专用所有权标记，并已登记到当前 E2E Workspace；
6. 卸载字符串精确指向记录的安装目录；
7. 目标不是 reparse point，也不包含越界的父级关系。

任一条件不满足时立即失败，不尝试补偿性删除。测试还要创建一个未登记的外部哨兵目录，证明 `/DELETEPROJECTS` 不会删除 Workspace 注册表之外的内容。

工作流收尾只能终止安装记录中身份匹配、且可执行路径位于记录安装根或 Runtime 根内的进程。禁止按进程名批量结束，也禁止递归删除未验证路径。

## 7. E2E 支撑接口

在现有 `InstallerHarness` 上扩展明确的高层动作，而不是让测试直接拼接 PowerShell 参数：

- 构建或读取基线版与候选版元数据；
- 安装指定场景制品；
- 捕获升级前后状态快照；
- 执行默认卸载；
- 执行只删除应用数据；
- 执行删除应用数据和项目；
- 验证卸载选项联动；
- 保存脱敏报告。

PowerShell 脚本继续负责 Windows 安装器、注册表、快捷方式和进程边界；TypeScript 世界对象负责业务状态、Runtime 夹具、项目、会话和跨阶段断言。两层通过结构化 JSON 记录交互，错误不能只表现为脚本退出码。

现有成功路径保留并拆成可复用阶段，避免为完整生命周期复制一套项目创建和会话断言。卸载后的场景重建由 Harness 显式完成，不能由测试文件直接清理固定用户目录。

## 8. CI 工作流

新增独立 Windows 安装生命周期工作流，至少支持：

- `quick`：PR 默认模式；
- `full`：每日计划和手动 RC 模式；
- `release-compat`：手动提供上一正式 Release 资产的兼容模式。

工作流设置单实例并发，避免同一 Runner 上多个安装器争用注册表、产品名或端口。各阶段设置独立超时，失败和取消时仍执行受控进程收尾和制品上传。

上传制品保留 14 天，内容包括：

- 脱敏生命周期报告；
- 构建元数据和安装记录；
- Generation 时间线；
- WebDriver 截图；
- 失败阶段与结构化状态差异；
- 不包含认证头和正文的夹具请求摘要。

PR 路径过滤至少覆盖安装器模板、Tauri 壳、Runtime 管理、Profile、项目、Session 投影、E2E 支撑代码和工作流自身。即使普通双平台构建成功，Windows 安装生命周期门禁失败时也不能视为可发布。

## 9. 脱敏和诊断

报告生成前统一执行脱敏：

- 仓库路径替换为 `$REPO_ROOT`；
- E2E 根替换为 `$E2E_ROOT`；
- Windows 用户目录替换为 `$USER_HOME`；
- 临时目录替换为 `$TEMP`；
- 端口、PID 和时间戳仅在必要时记录；
- API Key、Authorization、Cookie、提示词和回复正文禁止进入报告。

测试标记可以记录固定摘要或哈希，不保存用户式自由文本。脱敏后执行敏感信息扫描；扫描失败时不上传原始报告，只保留最小错误类别。

## 10. 测试与验收

### 单元与约束测试

- 临时基线版本严格小于候选版本。
- 双安装包元数据完整且 SHA-256 可复算。
- 卸载命令三个有效组合和联动规则正确。
- 删除脚本拒绝缺少所有权标记、越界路径和错误卸载字符串。
- 报告能替换绝对路径并删除凭证和正文。

### PR 快速门禁

- 安装阶段无 Runtime 下载；
- 首次启动只准备一次 Runtime；
- 温启动不重复准备；
- Unicode 项目和两个会话无需刷新；
- 重启恢复；
- 默认卸载保留全部哨兵。

### 每日与 RC 门禁

- 基线版到候选版真实覆盖升级；
- 升级前后快照满足全部不变量；
- 升级后继续对话并二次重启；
- 三个有效卸载结果；
- 项目删除自动联动应用数据删除；
- 未登记外部目录始终保留；
- 输出脱敏报告。

### 人工发布验收

安装版连续完成 30 轮创建、回复和切换，不出现空白、重复会话和刷新依赖。该人工门禁记录在 Release Candidate 验收表中，不伪装成 CI 自动化结果。

## 11. 完成条件

- PR 快速工作流在相关变更上稳定运行。
- 每日或手动完整工作流能够从零构建双安装包并完成升级与卸载矩阵。
- 任一失败都能定位到稳定阶段，并提供脱敏证据。
- 升级不丢失 Profile、last-known-good、Runtime、项目、会话和模型路由。
- 默认卸载不删除用户数据；显式删除只影响用户确认且属于当前 E2E 场景的目标。
- `doc/README.md` 更新 P0.2 状态和下一开发入口。
